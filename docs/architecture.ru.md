# Как устроена Evelent DB (простыми словами)

Этот документ объясняет устройство базы так, чтобы можно было чинить
производительность и не ломать данные.

## За 30 секунд

У тебя **одна программа** (`server/`), внутри которой живут три вещи:

1. **Документы** — как Mongo: коллекции, `_id`, фильтры, индексы. Лежат на диске.
2. **KV (как Redis)** — строки, TTL, hashes/lists/sets. Живут в RAM + снимок на диск.
3. **Pub/Sub** — рассылка сообщений по каналам (без диска).

Клиенты ходят по **HTTP/JSON**. Отдельного процесса Mongo/Redis нет.

```
Клиент (SDK / curl / GUI)
        │  HTTP
        ▼
   server (handlers)
        │
   ┌────┴─────┐
   ▼          ▼
Документы    MemStore (KV)
(сегменты)   (sharded LRU)
```

## Документы: как пишется и читается

### Запись (Insert / Update)

1. Документ → JSON → **AES-256-GCM**.
2. Шифротекст **дописывается в конец** файла `segments/000001.seg`
   (когда файл > 64 MiB — открывается следующий).
3. В памяти обновляется карта **`.docindex`**: `_id → (номер сегмента, offset, длина)`.
4. Если есть secondary indexes — обновляются в памяти.
5. **На диск meta не пишется сразу** (это важно для скорости).
   Раз в ~1 секунду dirty docindex/indexes сбрасываются; при `Close` — обязательно.

Update **не затирает** старые байты: пишется новая запись, указатель в docindex
переезжает. Старые байты — «мусор», пока не сделают **Compact**.

Delete убирает `_id` из docindex; байты в сегменте тоже ждут compaction.

### Чтение по `_id`

1. Смотрим **hot cache** (LRU до 8k документов / 64 MiB на коллекцию).
2. Иначе берём координаты из docindex → читаем из сегмента через **кэш FD**
   (файл не открывается заново каждый раз) → decrypt → JSON.
3. Старые legacy-файлы `docs/xx/id.json` ещё читаются, если есть.

### Find (поиск)

| Ситуация | Что происходит |
|----------|----------------|
| Фильтр `{field: value}` и есть индекс | Hash-lookup по индексу → загрузка только нужных id |
| Фильтр `{age:{$gte:18,$lt:65}}` и есть индекс | **Range** по отсортированным бакетам индекса |
| Нет индекса / сложный фильтр | Полный проход по живым id (дорого на больших коллекциях) |

**Правило:** на поля, по которым часто ищешь — делай индекс.

```http
POST /api/collections/users/indexes
{"field":"age"}
```

## На диске выглядит так

```
<data-dir>/
├── .key                 # ключ AES (или DB_ENCRYPTION_KEY)
├── .kvstore             # снимок KV
└── users/               # коллекция
    ├── .docindex        # id → где лежит документ (бинарный формат)
    ├── segments/
    │   ├── 000001.seg
    │   └── 000002.seg
    ├── docs/            # legacy (старый формат)
    └── indexes/
        └── age.idx
```

## Durability (насколько «железно» на диске)

Флаг сервера: `-sync-mode`

| Режим | Что делает | Когда брать |
|-------|------------|-------------|
| `none` (по умолчанию) | Сегменты не fsync'аются на каждый write | Максимальная скорость, dev / кэш |
| `every_sec` | fsync грязных сегментов ~раз в секунду | Хороший баланс |
| `every_write` | fsync после каждой записи документа | Максимальная durability, медленно |

Meta (docindex) всё равно flush'ится фоном ~1с и на shutdown.

```bash
./db.exe -port 8080 -data-dir ./data -sync-mode every_sec
```

## KV (MemStore)

- Данные в RAM, шардированный LRU (меньше contention).
- Снимок `.kvstore` каждые ~5 секунд, если были изменения.
- RMW-команды (INCR, HSET, LPUSH…) берут **striped lock по ключу**, а не один глобальный.

Не клади в KV гигабайты «как в Mongo» — это кэш/сессии/очередь, не холодное хранилище.

---

## Compaction

Переписывает живые документы в новые сегменты и удаляет старые файлы с мусором.

- Автоматически, если live-байты < 50% размера сегментов и суммарно > 8 MiB (~раз в 30с проверка).
- Вручную: `Collection.Compact()` / `Database.CompactAll()` из кода.

## Что уже ускорено (кратко)

| Узкое место раньше | Сейчас |
|--------------------|--------|
| Полный rewrite `.docindex` на каждый write | Batched flush ~1с |
| `os.Open` на каждый read | FD-кэш сегментов |
| Каждый Get с диска | Document hot LRU |
| AES NewGCM на каждый вызов | Reuse AEAD |
| Index Delete O(n) по списку | Set O(1) |
| Только equality index | + range `$gt/$gte/$lt/$lte` |
| Docindex как огромный JSON | Бинарный gob (`EDIX`) |
